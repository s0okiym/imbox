## 已定位问题与后续验证

1. 每次传输 ACK 重复数据库认证/订阅检查，放大读负载。ACK 现在只释放当前连接确实送达过的窗口；订阅与派发前仍重新检查权限。新增伪造 ACK 拒绝测试，原有撤权和背压回归继续运行。
2. 通知来源 UNION 中使用易变 `clock_timestamp()`，阻止 CTE 内联，逐事件查询可能展开整租户历史。调整为当前 SQL 语句时间及允许条件下推；过期与当前权限语义保留。通知集成 9 项通过；探针增加实际查询计划的消息扫描行数、是否全来源物化及执行时间。
3. 探针增加脱敏服务端错误代码统计，区分 SQL 超时与其他错误，不输出请求头、SQL 参数或私人正文。

## 短测定位（与完整百万历史结果分开）

均为 1,000 连接 / 50 消息每秒 / 10 秒，历史缩为 1,000 条，仅用于缩短定位周期，不替代完整规模准出。

| 改动 | 保存 P95 | 提交后可见 P95 | 保存 / 请求 | 说明 |

| 仅合并并发相同读取 | 14,932.62 ms | 16,402.47 ms | 500 / 500 | 空轮询重新加密游标导致逻辑相同位置分裂为不同键，合并效果不足。 |

三个短测均无 HTTP 错误、断连或重复送达。源查询计划保持检查 1 条消息。并发 projector 使用一次批量领取、默认 4 路不同会话并行，同一会话保留顺序；新增真实数据库行锁用例证明一个会话阻塞时另一个仍可推进。仍须进一步测量数据库/连接池/IO 等待和完整负载。


## 测量完整性修正

探针 v2 在事务成功返回时记录已提交消息和对应订阅连接数，分别统计 HTTP 保存成功、数据库已提交消息、应送达份数、实际唯一送达份数与缺失份数。发送结束后最多等待 60 秒排空，仍有缺失时将延迟样本标记为截尾，不能把已收到子集的 P95 解释成全部收件人的 P95。该修正已执行下述短测；不会追溯改变上表旧报告的结果。探针仍需补齐参考身份/空间分布、重连与竞争场景。

## 历史页批量读取（14:39～14:45 UTC）

消息分页原先对每条消息分别查询作者、附件、反应和编辑时间；普通 100 条历史页因此有数百次数据库往返。现在批量读取页内元数据，保留事务内当前授权、租户过滤、消息顺序，以及引用来源的可见范围和删除判断。查询次数回归限制普通页面从 10 条增至 100 条时不按行增加查询；混合作者/编辑/反应/固定引用与删除另有真实数据库断言。

同样 50 连接 / 1,000 历史 / 5 秒短测，历史页 P95 从先前 497.93 ms 降至 40.13 ms。两次尝试将相同批量查询用于单条读取时，发送 P95 为 1,326.56 / 1,482.06 ms；保留原单条查询路径后仍为 1,399.11 ms，不能据此断言发送差异由批量查询导致，也不能宣称写入性能已改善。最终实现仅对历史页和线程页使用批量读取。
