# 消息联合故障与 ACK 积压恢复

日期：2026-10-05（Asia/Shanghai），父候选 a3dbabf。

同一租户、同一次运行组合以下故障：模型真实 HTTP 请求挂起并最终断开；上传的本机故障代理返回 503，恢复后转发到真实 SeaweedFS S3；接收者 WebSocket 被终止；投影消费暂停。期间通过真实认证 HTTP API 提交 60 条消息，其中 6 条用相同命令键/客户端消息 ID 重试。断言重试返回原 ID、数据库 outbox 实际积压、接收端游标尚无新投影。数据库始终可用，没有声称覆盖数据库整体故障。

模型断开后 Run 保持 waiting_dependency、输出为空、预留状态 unknown；再次调度不增加模型调用。对象代理恢复后复用原签名上传票据写入真实 S3，完成确认核对 SHA-256。重新创建投影消费者处理持久积压，接收者从原游标重连，核对所有 60 条正文；再发送一条在线消息，网络接收及数据库均为 61 个唯一消息 ID，无遗漏或重复。

首轮 15 项同步回归中 14 通过，联合场景在恢复后的在线消息等待处失败。增加不包含凭证/正文的阶段诊断后确认：重放消息均已收到，集中发出的 60 条合法 ACK 超过异步输入队列的 32 帧限制，连接被服务端关闭。此路径与当前 Web 客户端逐条确认协议一致，不能通过降低消息数量或延长等待来规避。

修复把已完成握手的合法 ACK 作为同步、本地、有界窗口操作处理，不排入异步认证/订阅队列。仍校验完整帧契约、现存订阅及实际已送达游标；ACK 不改变已读、当前授权或业务状态。未完成握手的 ACK 拒绝；其他控制帧继续受 32 项队列上限约束，发送窗口和背压上限不变。补充握手与伪造 ACK 同批发送的拒绝测试。测试等待器也在连接已关闭时立即失败，避免误报为网络超时。

初步修复后原 15 项同步测试全部通过（19.99 秒）。最终完整 pnpm verify 通过，含 191 单元（10.14 秒）；同步、模型驱动与资源三文件 32 项集成全部通过（31.78 秒）。三项真实 Chromium 消息场景通过（40.4 秒含启动；双人通信/编辑撤回 12.1 秒，丢响应及移动布局 7.6 秒，未知展示降级 7.3 秒）。历史兼容六场景通过（51.4 秒含启动，不含历史构建）：四项历史 Action 编译服务集成，以及两项 Web/API 浏览器场景（9.9 / 16.9 秒）。不能把四项服务集成计入浏览器数量。回归目录 89 文件 / 538 声明，验收仍 30/41 且按预期非零退出。初次新测试的类型检查把 StreamEvents.items 误写为 events，已按原契约修正，不修改生产响应。

范围：这是有界的组合故障回归，不是长期压力演练。模型使用可控 HTTP 协议服务，不是该轮真实推理质量验证；投影通过暂停调用并重新创建处理器恢复，不冒充杀死独立 Worker 进程；S3 通过隔离传输代理注入故障，不停止共享基础设施。长期积压、跨进程崩溃、数据库/队列联合故障及参考容量仍需单独验证，AC-16 保持 partial。
